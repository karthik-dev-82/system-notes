Priority Inversion: Play With It

The bug that nearly stranded the Mars Pathfinder rover in 1997. A low-priority task holds a mutex; a high-priority task needs it and blocks; a medium-priority task that needs neither keeps preempting the low-priority one -- so the mutex never gets released, and the high-priority task waits far longer than its priority should ever allow.

Worth knowing, beyond what's animated here
  • This is a real, historical bug, not a hypothetical. NASA's Mars Pathfinder rover started resetting itself on the surface of Mars in 1997 from exactly this scenario -- a low-priority "bus management" task holding a mutex, a high-priority "bus scheduler" task blocked waiting for it, and a medium-priority communications task repeatedly preempting the low-priority one. Engineers uplinked a fix that enabled priority inheritance, already present but disabled in the RTOS (VxWorks) the rover ran.
  • Priority inheritance doesn't eliminate waiting -- it bounds it. With it on, BusScheduler's wait is capped by BusManager's own critical-section length, however long that happens to be. Drag CommsTask's workload up and down with inheritance ON and watch BusScheduler's completion tick stay exactly the same across the whole slider range -- that invariance is the entire point. It specifically covers workload added on the path CommsTask already preempts after BusManager holds the mutex; a medium-priority task that delays BusManager before it ever acquires the mutex is a different problem inheritance can't fix, since inheritance only helps once the low-priority task actually holds the contested lock.
  • The fix costs something too. While BusManager holds the inherited high priority, it can preempt tasks that would otherwise have run -- including ones that have nothing to do with the mutex. Priority inheritance trades a small, bounded, deliberate unfairness for eliminating a much larger, unbounded, accidental one.
  • This widget models one mutex and direct hand-off to the highest-priority waiter on release, both real, common implementation choices -- not every RTOS mutex behaves identically, but the core mechanism (temporarily borrowing the waiter's priority) is the actual fix real systems, including Pathfinder's, actually shipped.
