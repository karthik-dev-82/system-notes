Worth knowing, beyond what's animated here
  • This is a real Kafka config, not a widget-only toggle. unclean.leader.election.enable defaulted to true in early Kafka and was flipped to false in Kafka 0.11 (2017, KIP-106) specifically because the old default silently favored availability over durability, catching operators off guard. It ships false in every Kafka release since.
  • Killing the leader triggers an election automatically -- exactly like this widget does it -- because Kafka's controller continuously watches broker liveness and reacts the moment the current leader stops being reachable. You never have to ask for an election explicitly unless the partition is already leaderless and you're retrying (the "Attempt Leader Election" button above only appears in that situation).
  • A rejoining broker doesn't just "catch up" -- it can get truncated. Force an unclean election, then click "Restart" on the old leader: notice it comes back holding messages the new leader doesn't have. Click "Catch Up" and watch its log shrink down to match the new leader's, not grow -- those extra messages are discarded, not merged. This is real Kafka replication protocol behavior (a follower truncates to the leader's log before fetching forward), not a simplification.
  • This is the exact same tradeoff as the CAP theorem widget, wearing Kafka's real names: leaving unclean.leader.election.enable off is the CP choice (refuse to serve rather than risk silently losing acknowledged data); turning it on is the AP choice (restore availability immediately, accept the data-loss risk). min.insync.replicas paired with acks=all is Kafka's other CP-leaning knob -- it rejects a write outright rather than accept one that isn't durably replicated widely enough, the same shape of refusal the CAP widget's CP mode makes for reads and writes during a partition.
