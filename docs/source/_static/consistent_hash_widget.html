Worth knowing, beyond what's animated here
  • The rule for finding a key's server is always the same: walk clockwise from the key's position until you hit the first server point. That's the entire algorithm -- everything else (virtual nodes, rebalancing) is about making that rule behave well, not changing the rule itself.
  • Try the virtual-node slider at 1 a few times via Reset -- notice the "keys per server" distribution can be quite lopsided depending on where the servers' single points happen to land. That's real, not a bug: with one point per server, whichever server happens to own the largest arc gets the most keys, purely by chance of where its hash landed. Turning virtual nodes up spreads each server across many small arcs instead of one big one, and the total (the sum of many small, mostly-averaging-out arcs) balances out far more reliably. This is exactly the caveat mentioned on the main Hash Load Balancer page.
  • The "naive modulo" percentage shown after each add/remove isn't a fixed number -- it's recomputed live for the exact same key set and the exact same before/after server count, so it's a fair, direct, apples-to-apples comparison against what actually happened on the ring.
  • Real systems (Cassandra, DynamoDB-style partitioning, many CDNs and client-side sharding libraries) use this exact idea, almost always with virtual nodes, sometimes numbering in the hundreds per physical node specifically to keep the load-balance tight even as nodes are added and removed over the system's lifetime.
