CAP Theorem: Partition a 2-Node Store

Two replicas hold the same key. A network link connects them. Break the link, then pick a policy for what each side does about reads and writes while it can't reach the other -- that choice is the CAP tradeoff, made concrete instead of abstract.
Try this: write a value to Node A (watch it replicate to B) → break the network → switch to CP and try writing/reading either node (both refuse) → switch to AP and write different values to A and B (both succeed -- now they disagree) → heal the network → notice they're still disagreeing until you click Reconcile.

Worth knowing, beyond what's animated here
  • CAP is not a static "pick 2 of 3" menu. A distributed system that replicates data always gets Consistency and Availability when there's no partition -- the tradeoff only exists during an actual partition. That's why nothing interesting happens in this widget until you click "Break the Network."
  • In CP mode with only two nodes, breaking the link makes both sides unavailable, not just one. Neither side can prove it's the "real" one without hearing from the other, so a strict consistent system has no safe choice but to refuse everyone. Real CP systems (etcd, Raft/Paxos-based stores, ZooKeeper) fix this by running an odd number of replicas so a majority side can keep serving -- see the companion quorum widget below.
  • Flipping the policy toggle to CP does not retroactively fix data that already diverged under AP -- it only governs what happens to future requests. If A and B already disagree, they keep disagreeing until you explicitly heal the network and click Reconcile. This is not a simplification for the demo -- it's exactly how a real switch from an "AP mode" to a "CP mode" config would behave, since the label doesn't move any bytes.
  • Reconciliation here uses last-write-wins by timestamp ("clock"), the same strategy real systems like Cassandra use by default. Notice what it does: the losing write is silently discarded, with no merge. That's a genuine, documented weakness of naive LWW under concurrent writes -- if the two clocks were wall-clock timestamps from two different machines with any clock skew, "later" isn't even guaranteed to mean "actually happened later." Systems that need to avoid silently losing writes use vector clocks or CRDTs instead, which can detect a genuine conflict rather than guessing a winner.
  • This is the same idea as strong vs. eventual consistency: CP behavior here is a strong-consistency read/write (refuse rather than risk stale data); AP behavior here is eventual consistency (serve immediately, converge later).
