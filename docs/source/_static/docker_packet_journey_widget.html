Worth knowing, beyond what's animated here
  • PREROUTING and POSTROUTING aren't "the inbound hook" and "the outbound hook" -- every packet passes through both, in that fixed order relative to the routing decision, on every interface. Whether either one actually rewrites anything depends entirely on which rules match. This widget highlights whichever hook does real work for the leg you're watching and shows the other as a pass-through, but both are genuinely traversed every time.
  • The real MASQUERADE rule Docker installs is iptables -t nat -A POSTROUTING -s 172.17.0.0/16 ! -o docker0 -j MASQUERADE -- it only fires when traffic from the container subnet is leaving via something other than docker0 itself, which is exactly why container-to-container traffic over the bridge is never MASQUERADEd.
  • conntrack is what makes the reply leg automatic. NAT rules are only consulted for the first packet of a new connection; every packet after that -- including replies travelling in the opposite direction -- gets rewritten straight from the tracked connection entry, without re-walking the rule chains. You can see the live table on a real system at /proc/net/nf_conntrack.
  • MASQUERADE can also rewrite the source port, not just the source IP, when two different containers happen to pick the same ephemeral port for an outbound connection at the same time -- the host has only one IP to hide them all behind, so ports are what keep their connections distinguishable. This widget keeps the port fixed for one connection to keep the walkthrough readable.
  • This entire hub -- PREROUTING, the routing decision, FORWARD, POSTROUTING -- is iptables acting as a frontend to netfilter, the actual packet-filtering engine built into the kernel. Newer systems increasingly use nftables instead, but the hook points and this ordering are the same concept either way.
