Worth knowing, beyond what's interactive here
  • The leftmost prefix rule is exactly what it sounds like. A B-Tree composite index is sorted by its first column, then by its second column within each value of the first, and so on. Skip the first column entirely and the rest of that sort order is useless for narrowing a search -- there's no way to jump straight to "currency = EUR" in an index sorted by region first.
  • A range condition is the last column usable for seeking, even if later columns have their own conditions. The index can narrow down to "everyone in Europe, population between X and Y" in one seek, but anything after that range column has to be checked row by row on whatever the seek already turned up -- the sort order past a range isn't reliable anymore.
  • "Usable for seeking" and "covering" are two different, independent properties. A column that can't be used to narrow the search can still be read for free if it's part of the index -- composite indexes store every one of their columns together in each entry. A query only needs a full table row (an extra lookup per matching row) if it needs a column the index doesn't carry at all.
  • Column order is a real design decision, not a formality. Reorder the same two columns in the index definition above and watch which queries suddenly stop being able to use it at all.
