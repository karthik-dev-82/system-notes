Worth knowing, beyond what's animated here
  • Why this format self-syncs: a continuation byte always looks like 10xxxxxx, and no lead byte ever does -- so a decoder that starts reading in the middle of a multi-byte character (a truncated network read, a random file seek) instantly recognizes it landed mid-character and can skip forward to the next real boundary. No other variable-length scheme of the era had this property by construction.
  • ASCII is not just "compatible with" UTF-8 -- it's a strict subset. Any valid ASCII file is already valid UTF-8, byte-for-byte, because every ASCII byte is ≤ 0x7F and every UTF-8 single-byte character is defined as exactly that range. This is why UTF-8 could replace ASCII everywhere without a flag day.
  • Overlong encodings are illegal, on purpose. The bits for U+0041 ('A') technically fit inside a 2-byte template too, but a conformant decoder must reject that as invalid rather than accept it as an alternate spelling of 'A'. Early decoders that didn't enforce this were exploited to smuggle ../ and other filtered characters past security checks that only scanned for the 1-byte form.
  • JavaScript strings are UTF-16 internally, not UTF-8. That's exactly why this widget iterates with code-point-aware logic instead of raw indexing: an emoji like 😀 is one Unicode code point but two UTF-16 code units (a surrogate pair), so naive string[i] access would split it in half. Python 3 strings avoid this entirely by storing code points directly.
