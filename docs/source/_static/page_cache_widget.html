Worth knowing, beyond what's animated here
  • Every regular file read in Linux goes through the page cache -- there's no way to opt out short of O_DIRECT. Ask for a single byte and the kernel still pulls in the whole containing 4 KB page, on the theory that you'll probably want the rest of it soon (and it's barely more expensive to fetch 4 KB than 1 byte at these latencies anyway).
  • This is the actual answer to "why does I/O block?" from Multiprocessing vs Threading vs AsyncIO -- a cold page-cache miss is a real wait for a real disk (or network) round trip, tens to hundreds of microseconds even on fast NVMe storage, doing nothing useful the whole time. Threading and asyncio both exist to let something else run during exactly that gap; a warm page-cache hit, by contrast, is fast enough that there's rarely anything worth yielding for.
  • The kernel doesn't shrink the page cache just because it can. Free RAM that isn't caching anything is doing no work for you, so a healthy system's cache grows until memory pressure forces it to evict something -- that's why "available" memory looks low on a machine that's actually running fine.
  • write() returning doesn't mean your data is safe. This widget's crash button makes that concrete: anything written but never fsync()'d only ever existed in RAM. Database engines and anything else that can't tolerate silent data loss call fsync() (or open files with flags that force synchronous writes) specifically to convert "probably on disk soon" into "confirmed on disk, right now" -- at the cost of paying that full disk-latency price on every write instead of amortizing it in the background.
  • This widget skips one real behavior for clarity: read-ahead. A real kernel notices sequential access patterns and starts pulling in upcoming pages before you ask for them, so a sequential scan pays the miss cost far less often than this one-page-at-a-time model shows.
