Worth knowing, beyond what's interactive here
  • The logger's level is checked exactly once, before any sink ever sees the message. A sink set to trace will never emit a message the logger itself already rejected -- there's no way for a permissive sink to "override" the logger's cutoff. That's the detail that's easy to get backwards: it's not "whichever gate is most permissive wins," it's "the logger gates first, then each sink gates again independently."
  • Two sinks on the same logger can genuinely disagree about the same call. In the default configuration here (matching this project's own Quick Start Template), the console sink defaults to debug while the file sink defaults to trace -- so a trace-level call reaches the file but never the console, even though both are attached to the exact same logger.
  • set_level(spdlog::level::off) is a real level, not a special case -- it's simply one step past critical in the ordering, so nothing ever clears that gate. Try setting a sink to off and firing a critical call at it.
  • The patterns shown above (%T, %Y-%m-%d %H:%M:%S.%e, %n, %l, %v, and the %^/%$ color-range markers) are spdlog's real formatting flags, substituted here exactly as spdlog itself would -- not a simplified stand-in.
  • See Understanding spdlog Sinks & Architecture for the full write-up this widget is built from, including the rotating file sink mechanism this widget doesn't cover.
