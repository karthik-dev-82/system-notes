Worth knowing, beyond what's animated here
  • Try writing to /etc/hosts, watch the copy-up happen, then write to it again -- the second write does NOT copy up a second time, because it's already in the upperdir. The expensive part only happens once per file, on its first modification.
  • Switch to Container B and read /etc/hosts after Container A has already modified it. Container B still sees the original, unmodified lower-layer version -- each container's upperdir is completely private, even though they're both reading from the exact same shared lower layers. That isolation is what makes it safe for hundreds of containers to share one base image without stepping on each other.
  • Delete a file that only exists in the upperdir (try creating /app/data.txt first, then deleting it) and notice the log says it was removed directly, no whiteout. Whiteouts only exist to mask something that would otherwise show through from a lower layer -- if there's nothing underneath to hide, a real deletion is all that is needed.
  • The practical consequence the main docs page calls out is real: writing a single byte to a multi-gigabyte file that only exists in a lower layer copies the entire file up before the write can happen. That's the actual reason databases and other write-heavy workloads inside containers are normally pointed at a volume (which bypasses OverlayFS entirely) instead of writing straight into the container's own filesystem.
