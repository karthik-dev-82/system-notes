Exception Unwinding Through Destructors: Play With It

When an exception is thrown, every stack frame between the throw and the matching catch gets destroyed on the way there -- automatically, in reverse order, exactly like a normal return. RAII cleanup happens for free; manual cleanup gets skipped.
void process() {
FILE* f = fopen("data.txt", "r"); // raw handle
risky(); // throws
fclose(f); // never reached
}
void process() {
FileGuard f("data.txt", "r"); // RAII wrapper
risky(); // throws
// no fclose needed
} // f's destructor runs during unwind -- closes the file

struct Guard {
~Guard() { if (!ok) throw std::runtime_error("cleanup failed"); }

~Guard() noexcept { /* cleanup that cannot throw */ }

Worth knowing, beyond what's animated here
  • Stack unwinding on an exception uses exactly the same machinery as a normal function return -- every local object's destructor runs, in reverse order of construction, as its frame is destroyed. This is the whole reason RAII works as a general-purpose cleanup strategy in C++ instead of just a convenience: there's no separate "cleanup path" to remember, because the normal-return path and the exception path both go through the same destructor calls.
  • This is the third page in this series to show the identical bug shape: a cleanup step written as an ordinary statement, placed after the code that might not reach it. The heap-leak tab on the memory page skipped it via an early return; the non-virtual-destructor tab on the vtables page skipped it via a missing keyword; this page skips it via a thrown exception. RAII is the one fix that closes all three at once, because it doesn't depend on which path control takes -- only on the object's scope ending.
  • The noexcept on the "safe" destructor in tab 2 isn't just documentation -- if a function marked noexcept does throw anyway, the runtime calls std::terminate(). Whether unwinding happens first is implementation-defined by the standard, but GCC and Clang both terminate immediately, before unwinding even starts. Marking destructors noexcept (which they are *by default* since C++11, unless a base or member's destructor isn't) turns "please don't throw from here" from a convention into something the compiler can reason about.
  • The reasoning behind "never let a destructor throw" isn't specific to double-exceptions in the abstract -- it's that a destructor generally can't know whether it's being called during normal scope exit or while another exception is already unwinding through it. Since the consequence of throwing in the second case is std::terminate() (immediate program abort, no stack unwinding, no catch block, nothing), and a destructor has no way to check which situation it's in, the only safe rule is unconditional: don't throw from a destructor, ever.
