unique_ptr vs. shared_ptr vs. weak_ptr: Play With It

Three different answers to "who's responsible for freeing this," side by side.

unique_ptr -- exactly one owner, ever

shared_ptr + weak_ptr -- one control block, two very different relationships to it

Worth knowing, beyond what's interactive here
  • A weak_ptr existing never keeps the object alive. Copy a shared_ptr, create a weak_ptr from it, then drop every shared_ptr -- the object dies immediately, with the weak_ptr just quietly becoming expired. It never contributed to the strong count, so it never had a vote in when the object dies.
  • You cannot conjure a brand-new shared_ptr once the object is gone. The "copy a shared_ptr" button disables itself the instant the strong count hits zero -- there's nothing left to copy from. The only way to get a live shared_ptr back at that point is .lock(), and it correctly returns nothing once expired.
  • The control block can outlive the object. Once the last shared_ptr drops, the managed object is destroyed -- but the small bookkeeping block (the counts themselves) sticks around as long as any weak_ptr still references it. That's a real, small piece of memory that stays allocated purely so a lingering weak_ptr has something safe to ask "are you still there?"
  • unique_ptr doesn't have any of this machinery. There's no control block, no counting -- just one pointer and a promise the compiler enforces: copying is a compile error, full stop. That's why it's the default choice whenever ownership genuinely isn't shared; there's nothing to get wrong.
