Worth knowing, beyond what's animated here
  • Dirty reads never happen here, at any level -- and that's not a simplification. PostgreSQL's docs state plainly that Read Uncommitted "behaves like Read Committed" in Postgres, because its MVCC design makes seeing another transaction's uncommitted data structurally impossible -- there's nothing looser than Read Committed to actually implement. (Source: PostgreSQL docs, transaction-iso.html, Table 13.1.)
  • Postgres's Repeatable Read is stricter than the SQL standard requires. The standard only requires Repeatable Read to stop dirty reads and non-repeatable reads -- phantom reads are still technically allowed at that level. Postgres implements Repeatable Read as true snapshot isolation (one snapshot for the whole transaction), which happens to close off phantom reads too. Try the Phantom Read scenario at Repeatable Read to see this for yourself.
  • Write skew is the one anomaly Repeatable Read does NOT close, even in Postgres. Snapshot isolation (what Repeatable Read actually is) prevents two transactions from seeing each other's writes, but it does nothing to stop two transactions from each making a decision based on a snapshot that's about to become stale. Only Serializable -- which additionally tracks read-write dependencies between concurrently active transactions and aborts one side of a dangerous cycle -- closes this gap. This widget's Serializable check is a scoped, exact version of that detection for two concurrent transactions; real Postgres's SSI generalizes it to chains of three or more.
  • Every level here is checked against the exact same underlying MVCC visibility rule (a row version is visible only if its creator committed before your snapshot, and wasn't itself superseded before your snapshot) -- the only thing that changes between levels is when that snapshot gets taken: fresh per statement for Read Committed, once at BEGIN for the other two.
