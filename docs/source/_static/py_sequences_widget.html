What's happening right now
Enqueue always appends to the right end -- O(1) either way. The difference is dequeuing from the front. Watch the shift counter: in list mode it climbs every single dequeue; in deque mode it never moves, because deque is a doubly-linked chain of blocks with genuine O(1) access at both ends.

Worth knowing, beyond what's animated here
  • The list growth formula and the exact sequence 0, 4, 8, 16, 24, 32, 40, 52, 64, 76, ... shown here are copied straight from CPython's own source comment in Objects/listobject.c (list_resize), current as of Python 3.11+: new_allocated = (newsize + newsize/8 + 6) rounded down to a multiple of 4. Versions before 3.11 used a slightly different formula (newsize + newsize/8 + (newsize<9 ? 3 : 6), giving 0, 4, 8, 16, 25, 35, 46, ... instead) -- the exact numbers have changed across releases, but "over-allocate geometrically, not one slot at a time" has been true for a very long time and is why append() is described as O(1) amortized rather than O(1) outright.
  • pop() (from the end) is cheap in more than one way: not only does it not shift anything, CPython usually doesn't even shrink the underlying array -- it only reallocates to a smaller block once the length drops below half of the current capacity (also verified directly against list_resize). A list that grew large and then shrank back down can sit on a lot of reserved-but-unused memory for a while.
  • The balanced-parens check is the simplest member of a whole family: the same push-on-open/pop-on-close pattern is how real parsers validate JSON/XML/code nesting, how "matching bracket" highlighting works in every code editor, and -- not a coincidence -- how the CPU itself tracks function calls. See the C++ stack/heap page for that same call stack from the other side, as actual memory being pushed and popped by call/ret.
  • collections.deque is not "a list that's also fast at the front" -- it's a genuinely different structure: a doubly-linked list of fixed-size blocks of 64 elements each (verified against Modules/_collectionsmodule.c, BLOCKLEN), not one node per element the way a naive linked list would be. That block size is what gives it O(1) at both ends without paying a full pointer-chasing cost per element the way a plain linked list would.
  • Python's own documentation is explicit that list.pop(0) and list.insert(0, x) are O(n) and recommends deque for anything that regularly adds or removes from the front -- this isn't a minor style preference, it's the difference between an algorithm that's accidentally quadratic and one that isn't, the moment you queue/dequeue in a loop.
