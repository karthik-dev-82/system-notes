Same producer, same pace. In busy-wait mode the consumer never sleeps -- it keeps re-checking the queue as fast as it possibly can, whether or not anything is there, burning CPU the whole time. Worth knowing, beyond what's animated here
  • The race-condition demo breaks counter++ into three steps (read, increment locally, write back) because that's genuinely what it compiles down to at the machine level -- there's no single atomic "increment" instruction happening here, which is exactly why two threads can interleave in the middle of it.
  • Notice that "No Synchronization" doesn't always produce a wrong answer -- try stepping the threads in strict turns and you'll get the correct result even with zero locking. That's the genuinely dangerous part of race conditions: the bug is real and always possible, but it doesn't announce itself every run, which is exactly why they're notorious for passing testing and then showing up in production under load.
  • A mutex is a counting semaphore with N=1 -- there's no separate mechanism, just a special case. The general form shows up constantly in real systems: a database connection pool is a semaphore sized to the pool's connection limit; a thread pool's work queue is bounded the same way.
  • Real semaphores and mutexes differ in one important way this widget doesn't model: a mutex is normally expected to be released by the same thread that locked it, while a semaphore's release()/post() can legitimately be called by a different thread than the one that called acquire()/wait() -- that's what makes semaphores usable for signaling between threads, not just mutual exclusion.
  • Real condition variables always pair with a mutex (you saw this in the C++ code on the main page -- std::unique_lock plus std::condition_variable::wait): the mutex protects the shared queue itself, and the condition variable is what lets a thread release that mutex and sleep in one atomic step, so nothing can sneak in and change the queue in the gap between "check it's still empty" and "go to sleep."
  • The deadlock demo shows a 2-thread, 2-lock cycle, but the same idea generalizes: a deadlock is any cycle in the "who's waiting for whom" graph, and it can involve any number of threads and locks. Lock ordering (always acquire in the same global order) is one real fix; others include using a single coarser lock, a lock-free design, or a timeout that backs off and retries instead of waiting forever.
