shared_ptr: Play With It

Shared ownership via reference counting: any number of shared_ptrs can own the same block, and it's only freed once the LAST one is gone. That flexibility has a real cost -- see the second tab for the classic way it bites back.
auto a = std::make_shared<int>(100); // refcount = 1
auto b = a; // copy -- refcount++
auto c = a; // copy -- refcount++
// ... handles destroyed one at a time ...
// block is freed only when refcount reaches 0
What's happening right now
Create a, then copy it into b and c. Destroy them in any order you like -- the block only actually frees on whichever destruction happens to be the last one.

Worth knowing, beyond what's animated here
  • The reference count isn't stored in the object being managed -- make_shared allocates a small "control block" alongside it that holds the strong count, a separate weak count (for weak_ptr), and a deleter. Copying a shared_ptr copies the pointer to that control block and atomically increments its count; destroying one decrements it. This is also why make_shared is generally preferred over shared_ptr<T>(new T(...)) -- it can allocate the object and its control block in one heap allocation instead of two.
  • The increments and decrements are atomic specifically so that shared_ptr is safe to copy and destroy from multiple threads at once -- a real, load-bearing guarantee, not an implementation detail. What's not automatically thread-safe is the pointed-to object itself; two threads can safely both hold a copy of the same shared_ptr, but mutating *ptr concurrently still needs its own synchronization. See the threads & synchronization page for that half of the picture.
  • The cycle in tab 2 is not a contrived example -- it's the single most common way real programs leak memory with shared_ptr: any bidirectional relationship (parent/child trees where children also point back to their parent, doubly-linked structures, observer patterns where the subject holds refs back to observers) creates exactly this shape unless one direction is deliberately made a weak_ptr. The rule of thumb: the "owning" direction is shared_ptr, the "referencing back" direction is weak_ptr.
  • weak_ptr can't be dereferenced directly -- you call .lock() on it, which returns a real (temporary) shared_ptr if the object is still alive, or an empty one if it's already been destroyed. That's the other half of what makes it safe for back-references: it can observe whether the object is still there without ever keeping it alive on its own.
