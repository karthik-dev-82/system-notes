Why CP Doesn't Mean Everyone Goes Down

The 2-node widget above shows a strict CP system losing all availability during a partition -- with only two replicas, neither side can ever prove it's the majority. Real CP systems (Raft, Paxos, etcd, ZooKeeper) fix this with more replicas and a quorum rule: only the side that can't reach a majority goes dark.

Worth knowing, beyond what's animated here
  • Set cluster size to 4 and isolated group size to 2, in CP mode: both sides go unavailable, because 2 out of 4 is not a strict majority for either side. This is the textbook reason real quorum-based systems (Raft, etcd, ZooKeeper ensembles) are almost always run with an odd number of nodes -- an odd total can never split evenly, so one side always has a majority and the cluster always has an answer for who's in charge.
  • Set cluster size to 5 and drag the isolated group up to 4 -- now the "majority" side only has 1 node left, which also doesn't reach the threshold, so the whole cluster goes dark. A quorum system's fault tolerance is exactly floor(N/2) simultaneous failures/isolations it can absorb while a majority is still reachable -- 1 for a 3-node cluster, 2 for a 5-node cluster.
  • AP mode here ignores quorum entirely -- every reachable node just keeps answering with whatever it locally has, exactly like the 2-node widget's AP mode. That's more availability, at the cost that the majority and minority sides can independently drift apart, the same divergence risk shown there.
  • This quorum rule is also the seed of leader election in Raft and Paxos: a node can only become leader once it collects votes from a majority of the cluster, for exactly the reason a minority group here can't be trusted to keep serving -- it might not have the latest data, and it can't prove it does without hearing from enough of the rest.
