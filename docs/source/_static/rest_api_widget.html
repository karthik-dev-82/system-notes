Worth knowing, beyond what's interactive here
  • "Idempotent" means the resulting server state converges, not that the response is identical every time. Delete book 1 twice: the first call returns 204, the second returns 404 (there's nothing left to delete) -- two different status codes, but the server ends up in exactly the same state (book 1 absent) either way. That's what idempotent actually means per RFC 9110, and it's a common point of confusion.
  • PUT can create, not just replace. PUT /books/99 on an id that doesn't exist yet creates it and returns 201, exactly like POST -- the difference isn't "create vs. update," it's who chooses the URI. PUT requests a specific URI from the client; POST asks the server to pick one for a new subordinate resource under the collection. Try PUT /books/50 here.
  • PATCH is genuinely not guaranteed idempotent, and this widget can prove it, not just assert it. The "Increment views" preset sends {"op": "increment", "field": "views"} -- click Send twice and watch the value go up by 2, not converge. A PATCH that sets an absolute value would be idempotent in practice, but nothing about PATCH *guarantees* that -- unlike PUT, where idempotency is part of the method's contract.
  • GET is safe: it never appears in "what changed" because it can't. Sending GET requests never alters the server-state panel above, no matter how many times you send one -- try it against a path that doesn't exist and watch it 404 without touching anything else.
  • Real production REST APIs add authentication, pagination, rate limiting, and content negotiation on top of this -- but the request/response/status-code mechanics here, including the PUT-creates and PATCH-isn't-idempotent behavior, are the real HTTP semantics from RFC 9110, not a simplified version of them.
