Command Pattern: Undo/Redo, Play With It

Every action here -- add, move, recolor, delete -- is a command object carrying both a forward action and its exact inverse. Undo doesn't "go back in time"; it runs the inverse. Redo re-runs the original. Do something new after undoing, and the discarded branch is gone for good.

Worth knowing, beyond what's interactive here
  • A command must capture everything its inverse needs at creation time, not compute it later. Deleting a shape here stores the shape's full data (position, color, everything) inside the delete command itself -- by the time you hit Undo, the shape is long gone from the canvas, so there's nowhere else that data could come from. This is the one detail that's easy to get wrong when hand-rolling undo/redo, and it's exactly what a real std::function-based command object has to get right.
  • Undo/redo history is a stack with one live branch, not a tree. Do a few actions, undo a couple, then do something new -- the undone actions are gone permanently, not saved off to the side. Try it: undo twice, do something new, then hit Redo and watch it refuse to bring back what you just discarded.
  • In modern C++, a command is often just a lambda plus its inverse, not a class hierarchy: struct Command { std::function<void()> doIt, undoIt; }; captures everything it needs by closure. The Gang-of-Four version used a full abstract base class with a virtual execute()/unexecute() pair per command type -- std::function collapses that into one reusable struct.
  • Jumping to an arbitrary point in the history list (rather than clicking Undo/Redo one step at a time) is just repeated undo or redo under the hood -- there's no separate mechanism for it, which is exactly why a stack-based history can support it for free.
