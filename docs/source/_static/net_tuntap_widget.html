Worth knowing, beyond what's animated here
  • Both TUN and TAP are exposed to a userspace application through the exact same device node, /dev/net/tun -- which one you get is decided by a flag (IFF_TUN vs IFF_TAP) the application passes when it opens the device, not by anything different about the file itself.
  • Most VPN software (OpenVPN in its default mode, WireGuard) uses TUN specifically because a VPN only needs to move IP packets from one place to another -- there's no Ethernet segment to emulate, so carrying MAC headers over the tunnel would be pure overhead. TAP exists for the cases that genuinely need Layer 2: bridging a VM's virtual NIC into a real network, or emulating a physical Ethernet segment over a tunnel (bridged VPNs, some older enterprise setups).
  • "Can't be bridged" isn't a policy restriction on TUN -- it's a structural fact. A bridge's entire job is reading Ethernet frame headers (source/destination MAC) to learn and forward. A TUN device only ever produces bare IP packets with no MAC header at all, so there is nothing for a bridge to read. This is exactly the same bridge from the Bridge Interfaces demo -- it needs Ethernet framing to do its job, full stop.
  • The "kernel network stack" box in this demo is a simplification of a real, two-way path: an application also reads from the TUN/TAP device to receive packets/frames the kernel wants to send back out through it -- this demo only shows the direction VPN traffic usually gets discussed in (app -> kernel -> out to the tunnel).
