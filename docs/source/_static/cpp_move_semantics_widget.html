Worth knowing, beyond what's animated here
  • std::move is not a verb -- it doesn't move anything by itself. It's exactly one thing: a cast (static_cast<Buffer&&>(source)) that tells the compiler "you're allowed to treat this as movable." Nothing happens to source at the moment you call it -- the actual theft of the pointer only happens when that cast result is bound to a move constructor's (or move assignment's) parameter, which is why this widget's log always shows the cast and the construction as two separate facts.
  • The move constructor here is marked noexcept on purpose, and it's not just documentation -- standard containers like std::vector check for it. If a type's move constructor might throw, a growing vector will fall back to the (slower, but exception-safe) copy constructor when reallocating, specifically to avoid ending up with some elements moved and others not if an exception hits partway through. A non-throwing move constructor is what unlocks the fast path.
  • "Moved-from" doesn't mean "destroyed" -- source is still a perfectly real, live object after being moved from; it's just been left holding nothing (nullptr, size 0, in this Buffer's case). The C++ standard's actual guarantee for standard-library types is only "valid but unspecified state" -- safe to destroy or reassign, but its contents shouldn't be assumed. A well-written custom type, like this one, can promise something more specific (here: empty).
  • This is the same underlying mechanism as unique_ptr's move -- unique_ptr is really just a Buffer that owns exactly one object instead of an array, with the same "steal the pointer, null the source" move constructor. Move semantics generalize past smart pointers to any type that owns a resource -- file handles, sockets, and any RAII wrapper follow the identical pattern.
