Worth knowing, beyond what's animated here
  • This is genuinely how a Linux bridge works, not a simplification for teaching -- docker0, br0, and every other Linux bridge device really do maintain a MAC learning table (visible with bridge fdb show) and really do forward exactly this way: unicast if the destination is known, flood if it's unknown or broadcast.
  • A real bridge also ages out table entries it hasn't seen traffic from in a while (300 seconds by default on Linux) -- not modeled here, but it's why a device that's been silent for a long time gets flooded-to again the next time something tries to reach it, until it speaks up and gets relearned.
  • The "move" step in this demo mirrors something that happens for real: a container restarts and gets a fresh veth pair, or a physical machine gets plugged into a different switch port. The bridge doesn't need to be told anything -- it just relearns the MAC on whatever port it next sees traffic from, and silently updates the table.
  • This learn-and-forward behavior is exactly what a real hardware Ethernet switch does -- a Linux bridge is a software implementation of the same idea, which is why Docker can give every container a virtual "port" on a virtual "switch" (docker0) and have real Ethernet semantics (including broadcast, ARP, and MAC-based delivery) just work.
