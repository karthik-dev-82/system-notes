Worth knowing, beyond what's interactive here
  • This is real compression and real encryption, not a stand-in. CompressionStream('gzip') and crypto.subtle.encrypt with AES-GCM are both native browser APIs -- the exact same interfaces a production app would call. The byte counts above are genuine output sizes, not illustrative numbers.
  • Encrypted data doesn't compress because it's supposed to look random. A good cipher's output is (by design) indistinguishable from random noise -- and random noise has no repeated patterns for a compressor to exploit. Compressing it afterward can only ever add a few bytes of container overhead, never meaningfully shrink it.
  • Compress-then-encrypt is never worse, but how much better it is depends on the data. Switch to the UUID sample -- still a real win, just a smaller one, because a UUID list has less repeated structure than a sentence repeated 200 times. Encrypt-then-compress stays flat at roughly 100% of the original either way.
  • Both pipelines are genuinely nested decorators, not two unrelated functions. Encrypt(Compress(data)) and Compress(Encrypt(data)) both implement the same "take bytes, return bytes" interface at every layer -- that's what makes it Decorator rather than just "call two functions in some order": each wrapper only knows about the interface of the thing directly inside it, never the concrete type.
  • See the Command widget, the Singleton widget, the Observer widget, and the Strategy widget for the other modern-C++ pattern widgets in this series (modeled here in JS using real browser crypto/compression APIs, since the pattern itself is language-agnostic).
