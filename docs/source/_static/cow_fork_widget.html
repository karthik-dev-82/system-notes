Copy-on-Write After fork(): Play With It

fork() doesn't copy a single byte of memory. It shares every frame between parent and child and marks the writable ones read-only in both -- the very first write on either side is what actually triggers a copy, and only if anyone else is still holding on.

Worth knowing, beyond what's animated here
  • The "last owner" optimization is real, not simplified. Linux's do_wp_page() checks the page's reference count before deciding what to do. If it's 1 -- nobody else can possibly be looking at this frame -- the kernel just flips the write-protect bit off in place. No allocation, no copy, no wasted work. This widget models that exact check: fault a page down to its last reference, then write it again, and watch the frame id stay the same.
  • Page D never gets a COW flag, on purpose. A genuinely read-only mapping (e.g. a shared library's executable text) is already safe to share across fork() with zero copying, because nobody was ever allowed to write it in the first place. Forking it just shares the frame directly -- there's no "eventually written" case to prepare for, so the kernel never marks it COW. Try writing to it before and after forking: both always segfault, immediately.
  • This is the exact mechanism VMAs, Page Tables & the Lazy Kernel: Play With It foreshadows in its own notes: pages get marked read-only specifically so the first write faults, and that fault is the kernel's only cue that a copy is now needed.
  • Frame exhaustion is simplified here on purpose, the same way it is in the VMA widget -- a real kernel facing "no free frames" runs page reclaim before retrying rather than simply failing.
