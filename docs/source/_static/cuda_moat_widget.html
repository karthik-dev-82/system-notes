The CUDA Moat

Why one company's chips became the bottleneck for an entire industry — the hardware reason, the software reason, and how thousands of them get wired together into one machine.

Short answer: it's two separate stories people usually blend into one. Story one is genuinely about physics: neural networks are, underneath, almost entirely one repeated operation (multiplying and adding numbers, over and over), and GPUs are chips built from thousands of simple cores doing exactly that operation at once instead of a few complex cores doing it one at a time. That part is real, and it isn't NVIDIA-specific — any sufficiently parallel chip benefits.

Story two is about software, and it is NVIDIA-specific: CUDA is NVIDIA's own programming platform, and after fifteen years of libraries, tooling, and a few million trained developers being built on top of it, it's now the reason renting an NVIDIA GPU is the boring, safe choice even when competing silicon is technically comparable or cheaper. This page covers both halves, plus the interconnects that let a rack of these chips act like one giant computer.

§1

The one operation underneath it all why GPUs, at all

Strip away the hype and a neural network training or answering a prompt is, at the hardware level, mostly one thing happening billions of times: multiply two numbers, add the result to a running total — a multiply-accumulate. Almost the entire cost of running a transformer model is matrix multiplication, which is just that same operation done in a very regular, very repeatable pattern across huge grids of numbers.

A CPU is built to be good at a few different, unpredictable things in a row — branching logic, cache-dependent lookups, one thread of a complex program. It has a handful of powerful cores (8–64 is typical) and spends a lot of its transistor budget on guessing what instruction comes next. A GPU throws almost all of that away and instead builds thousands of small, identical cores that all execute the same instruction on different data at the same time — a design called SIMT, single instruction, multiple threads. For one unpredictable task, that's a bad trade. For multiplying every element of two enormous, regular matrices, it's exactly the right shape.

This half of the story has nothing to do with NVIDIA specifically. AMD's GPUs, Apple's GPU cores, Google's TPUs, and countless AI accelerator startups all exploit the same idea: throw parallelism at a workload that's regular enough to parallelize. The part that is NVIDIA-specific starts in the next two sections.

§2

Inside one GPU the silicon

NVIDIA's GPUs organize those thousands of cores into repeated blocks called Streaming Multiprocessors (SMs). Each SM is a self-contained unit: a cluster of general-purpose CUDA cores, a smaller number of specialized Tensor Cores built specifically to multiply small matrix chunks in one operation instead of many individual multiplies, a warp scheduler that decides which group of threads runs next, and a slice of fast on-chip shared memory. A current data-center GPU repeats this block well over a hundred times — NVIDIA's H100 has 132 SMs; Blackwell Ultra has 160.

This is the same idea explored in Beyond the Bridges for CPUs — putting memory as physically close to the compute as possible — just taken further. A CPU's DDR5 is a few centimeters away on the motherboard; a GPU's HBM is millimeters away on the same package.

§3

CUDA: the moat isn't the chip the actual craze

Here's the part that actually explains why one company, not "GPUs" generically, ended up capturing the value: the hardware described above is necessary but not sufficient. Somebody has to translate "multiply these two matrices" into instructions those thousands of cores can actually execute efficiently — and that's a genuinely hard compiler and library problem, not a hardware one.

CUDA is NVIDIA's own answer to that problem: a programming language extension, compiler, and runtime that only targets NVIDIA GPUs. On top of it sit libraries — cuDNN for neural network layers, cuBLAS for matrix math, NCCL for coordinating many GPUs — that NVIDIA has spent roughly fifteen years hand-tuning. PyTorch and TensorFlow, the frameworks almost everyone actually writes code against, are themselves built on top of those libraries. OpenCL is an open, vendor-neutral alternative to CUDA that runs on any vendor's hardware — and it largely lost anyway, because NVIDIA's tooling, documentation, and library performance stayed consistently ahead. AMD's ROCm is the current, more serious competitor, and reported benchmarks still put CUDA roughly 10–30% ahead on most compute-heavy ML workloads, though AMD's newest chips win specific workloads (very large models that need more memory than an NVIDIA GPU has) on hardware capacity alone.

This is why "just build a competing GPU" undersells the problem NVIDIA's competitors face. The silicon is the easier half. Matching a fifteen-year library head start, a reported ~4 million active CUDA developers as of 2026, and a decade of university courses and documentation built around one specific toolchain is a software and ecosystem problem, on top of a hardware one.

§4

Wiring thousands of them together the interconnect

One GPU, however fast, isn't enough to train a large model in a reasonable time — real training and large-scale inference runs across dozens, hundreds, or thousands of GPUs at once, which only works if they can talk to each other far faster than a normal expansion slot allows. This is the same "what connects to what, and how fast" question the rest of this series asks about CPUs, scaled up by several orders of magnitude.

There's one more version of this worth knowing: NVIDIA's Grace Hopper superchip fuses an ARM-based Grace CPU directly to a Hopper GPU with NVLink-C2C — 900 GB/s, cache-coherent, no PCIe slot involved at all — about 7× the bandwidth of a GPU sitting in a normal PCIe slot talking to its host CPU. It's a direct descendant of the same idea covered in Beyond the Bridges: the fastest link is the one that never has to leave the package.
