Worth knowing, beyond what's interactive here
  • The crash above is real, not decorative. Compiling the exact shape of Unsafe mode's C++ (a std::vector<Observer*> the subject iterates on every notify) and destroying one observer without unsubscribing produces a genuine AddressSanitizer: heap-use-after-free the moment notify() reaches it -- not a simulated error state. The observers before the destroyed one in the list really do get updated first; the ones after it never run at all, because the process is gone by the time the loop would reach them.
  • Unsubscribing before destroying works too -- in either mode. The bug isn't "raw pointers are always wrong," it's "nothing enforces that you remember to unsubscribe." Try the Unsubscribe button before Destroy in Unsafe mode: no crash, because the subject's list never had a chance to go stale in the first place. The discipline works; it's just manual, silent to skip, and only caught by whatever happens to run over that exact pointer afterward.
  • weak_ptr::lock() is what makes Safe mode safe. The subject stores a std::weak_ptr<Observer> per subscriber instead of a raw pointer. A weak_ptr doesn't keep the object alive and doesn't go dangling when it dies -- calling .lock() either returns a live shared_ptr or an empty one, safely, with no possibility of touching freed memory. This is the standard, idiomatic C++ fix for exactly this lifetime mismatch, not a widget-specific trick.
