Worth knowing, beyond what's interactive here
  • Class vs. vendor chip is the real distinction, not a widget simplification. A device that declares a standard USB class (CDC-ACM, Mass Storage, HID, UVC, UAC, Printer) in its descriptor gets claimed by a generic driver the kernel already ships -- that's why an Arduino Uno "just works" with no install step. A device with no standard class (declared as vendor-specific, 0xFF) can only be claimed by a driver that matches its exact VID:PID -- FTDI, CP210x, CH340, and PL2303 adapters all fall in this bucket.
  • /dev/ttyUSB* numbering is one shared pool across every vendor-chip driver, not a separate counter per chip. Plug in a CH340 clone and then an FTDI adapter and you get ttyUSB0 and ttyUSB1 -- never two independent "ttyUSB0"s. /dev/ttyACM* is CDC-ACM's own separate pool.
  • Freed indices are reused, but never retroactively. Unplugging ttyUSB0 makes 0 the lowest free index again, so the next vendor-chip device to bind gets it. But a device that's already bound and sitting at ttyUSB1 keeps that number for as long as it stays attached -- it does not get renumbered down to 0 just because a lower slot opened up. Try it: attach three vendor-chip devices, unplug the first, then toggle a driver off and back on for one of the others and watch its number survive unchanged.
  • The VID:PID pairs and node assignments here are representative examples for teaching the mechanism, not a database lookup -- the binding logic (class-match first, vendor-ID-match as the fallback, lowest-free-index allocation per shared pool) is the real thing being modeled.
