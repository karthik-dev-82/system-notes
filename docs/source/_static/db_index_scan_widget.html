Worth knowing, beyond what's animated here
  • The index doesn't always win. Its cost is 1 + matches for equality or log2(N) + matches for a range -- both still grow with the match count. Try "Antarctica" (0 matches, cost 1) against something unselective like population > 0 (matches all 20, cost ~25): the index still does a little extra work over a plain scan once nearly everything matches. Real query planners actually check this trade-off and fall back to a sequential scan when an index wouldn't help.
  • The range side is a real binary search, not a simplified stand-in -- it's the same upper_bound logic backing B-tree range scans, verified here against hundreds of random thresholds including every exact population value in the dataset (the classic place an off-by-one hides).
  • An index has a cost the scan doesn't: it has to be built and kept up to date. Every INSERT/UPDATE on an indexed column also updates the index -- that's the "takes up storage, slows down writes" trade-off the source guide mentions.
