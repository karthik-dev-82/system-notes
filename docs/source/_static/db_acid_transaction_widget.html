Worth knowing, beyond what's animated here
  • The foreign key check runs on every insert, transaction or not. A capital can never point at a country that doesn't exist -- that's enforced statement by statement. What a transaction actually protects against is different: it's the risk of the first statement's effect (Kenya, the country) surviving even though the second one (Nairobi, the capital) never made it in.
  • Try running twice in a row without resetting. Once Kenya has really been committed, running again fails immediately on the very first statement -- a genuine duplicate-key error, not the simulated one. Transactional and non-transactional modes behave identically here, because nothing ever got a chance to half-succeed.
  • "Incomplete" isn't the same as "invalid." A country row with no matching capital doesn't violate any constraint in this schema -- nothing requires every country to have one. It's still worth flagging, though: it's exactly the kind of quiet inconsistency a transaction exists to prevent when the two rows are supposed to arrive together.
