Worth knowing, beyond what's animated here
  • These read/update costs aren't a guessed formula. They were captured from a real EXPLAIN ANALYZE against an actual PostgreSQL 16 instance loaded with this exact dataset: the normalized read compiles to a Hash Join that fully scans BOTH countries (20 rows) and currencies (13 rows); the denormalized read compiles to a single Seq Scan on 20 rows. The update numbers are just as real -- updating EUR's symbol touches exactly 1 row in the normalized currencies table, and exactly 8 rows in the denormalized table, matching this dataset's real EUR-using-country count.
  • Try leaving one or two boxes unchecked in the denormalized update, then click "Apply Update." The result is a genuinely inconsistent table -- some EUR countries show the new symbol, some still show the old one -- with no error, no warning, nothing structurally wrong from the database's point of view. That's the actual cost of denormalization: not slower updates, riskier ones. The normalized side has no equivalent checklist at all, because there's only one row to update -- the anomaly isn't unlikely there, it's structurally impossible.
  • This tradeoff scales the way you'd expect: the read-cost gap (2 tables vs. 1) barely matters at 20 rows, but grows with the size of the shared reference table and the number of joins a real query needs -- while the write-cost and inconsistency-risk gap (1 row vs. N rows) grows directly with how popular a given shared value is. There's no universally correct choice -- read-heavy, rarely-changing reference data (product categories, currency codes) tips toward denormalizing; frequently-updated shared data tips hard toward normalizing.
  • Real systems often split the difference: normalize the source of truth, then maintain a denormalized read-optimized copy (a materialized view, a cache, a search index) that's rebuilt or invalidated on write -- getting the fast reads without hand-editing N duplicated rows directly.
