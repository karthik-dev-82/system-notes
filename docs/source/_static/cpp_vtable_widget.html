Virtual Functions & vtables: Play With It

Every polymorphic object carries a hidden pointer to its OWN class's vtable -- regardless of what type of pointer you're holding it through. That one fact explains both correct dynamic dispatch and the classic non-virtual-destructor bug.
struct Base { virtual void speak() { std::cout << "Base::speak\n"; } };
struct Dog : Base { void speak() override { std::cout << "Dog::speak\n"; } };
struct Cat : Base { void speak() override { std::cout << "Cat::speak\n"; } };
 
Base* p = new Dog();
p->speak(); // dispatches through p's vptr -- calls Dog::speak
struct Base { void speak() { std::cout << "Base::speak\n"; } }; // NOT virtual
struct Dog : Base { void speak() { std::cout << "Dog::speak\n"; } };
struct Cat : Base { void speak() { std::cout << "Cat::speak\n"; } };
 
Base* p = new Dog();
p->speak(); // resolved at COMPILE TIME from p's type (Base*) -- calls Base::speak

struct Base {
~Base() { std::cout << "Base::~Base\n"; } // NOT virtual
};
struct Derived : Base {
int* resource = new int(99);
~Derived() { delete resource; std::cout << "Derived::~Derived\n"; }
};
Base* p = new Derived();
delete p; // only Base::~Base runs -- Derived::~Derived is SKIPPED
struct Base {
virtual ~Base() { std::cout << "Base::~Base\n"; }
};
struct Derived : Base {
int* resource = new int(99);
~Derived() { delete resource; std::cout << "Derived::~Derived\n"; }
};
Base* p = new Derived();
delete p; // dispatches through the vptr -- Derived::~Derived runs, then Base::~Base

Worth knowing, beyond what's animated here
  • The vtable and vptr aren't in the C++ standard at all -- the standard only mandates the behavior (a virtual call dispatches based on the object's real type). Vtables are simply how every major compiler (GCC, Clang, MSVC) actually implements that behavior: one shared table of function-pointer slots per polymorphic class, and one hidden pointer per object -- typically the first few bytes of the object itself -- pointing at its class's table.
  • The object's vptr is set during construction and never depends on how you're currently referring to the object. That's the entire mechanism in one sentence: a Dog object's vptr points at Dog's vtable the instant it's constructed, whether you access it through a Dog*, a Base*, or a Base& -- which is exactly why virtual dispatch through a base pointer still reaches the derived override.
  • Tab 2's bug is real, cited undefined behavior, not a style nitpick: the C++ standard explicitly calls out that deleting an object through a pointer to a base class with a non-virtual destructor, when the object's actual type is a derived class, is undefined. In practice this usually means exactly what the demo shows (the derived part silently never gets destroyed) rather than a crash -- which is what makes it dangerous: it can ship and run for a long time before anyone notices the leak.
  • The fix is one word for a real reason: any class meant to be deleted polymorphically (through a base pointer) needs virtual ~Base() {} -- even if the destructor's body is empty. This is why so many base-class style guides simply say "if a class has any virtual function, give it a virtual destructor too": it's cheap insurance against exactly this bug, and the cost (one vtable slot) is the same either way once the class is already polymorphic.
  • This connects directly to the heap-leak page and the RAII page -- a skipped Derived::~Derived() is exactly the same shape of bug as forgetting delete on one code path, just triggered by a missing keyword on a base class instead of a missing line at a call site. std::unique_ptr<Base> doesn't fix this by itself either -- it still calls delete on the raw pointer it holds, so the base class still needs a virtual destructor for that deletion to be correct.
