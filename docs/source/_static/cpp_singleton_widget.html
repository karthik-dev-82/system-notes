Worth knowing, beyond what's interactive here
  • "Magic statics" is the common informal name for a real C++11 guarantee -- the standard itself doesn't use that phrase, it just requires that concurrent execution shall not enter the initialization of a function-local static variable while it's already being initialized by another thread. The compiler inserts a hidden guard variable and blocking synchronization around it automatically -- that's the entire mechanism this widget models as the Safe mode.
  • The Unsafe mode isn't a strawman. if (!instance) instance = new T(); with no lock was a genuinely common pre-C++11 pattern, and it fails in exactly the way shown here: two threads can both read instance as null before either one's write lands, so both construct, and whichever write finishes last silently wins -- the other thread's object is orphaned, not an error, just quietly wrong. Try spacing the arrival ticks far apart in Unsafe mode: with no overlap, it behaves correctly, which is exactly why this class of bug is so easy to ship undetected.
  • Blocking, not busy-waiting, is the point. In Safe mode, a thread that arrives while another is already constructing doesn't spin or retry -- it blocks until construction completes, then proceeds with the fully-built object. No thread ever observes a partially-constructed singleton.
  • Double-checked locking (checking, then locking, then checking again) was the classic hand-rolled fix for this before C++11 -- and was itself notoriously easy to get wrong without a properly-placed memory fence. A function-local static makes the entire pattern unnecessary to write by hand.
  • The bigger caution: getting the synchronization right doesn't make Singleton a good default. It's still global state with the ability to be reached from anywhere, which makes testing and reasoning about dependencies harder -- prefer passing dependencies in explicitly where you can.
