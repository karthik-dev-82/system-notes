Worth knowing, beyond what's animated here
  • Token bucket and leaky bucket, configured this way (capacity = limit, refill/leak rate = limit/window), are mathematically dual -- run the same burst through both and they make identical allow/deny decisions every time. The real production difference isn't the admission decision at all: leaky bucket is usually implemented as an actual queue that releases admitted requests at a constant output rate (adding latency, but smoothing traffic downstream), while token bucket just gates admission and lets accepted requests straight through. This widget only models the admission decision, which is why they read as identical here.
  • Fixed window's flaw is structural, not a tuning mistake: it resets its counter at fixed clock boundaries regardless of when requests actually arrived, so up to 2 x limit requests can land in a window's worth of real time if they straddle a boundary. Sliding log fixes this exactly, at the cost of storing every timestamp in the window (unbounded-ish memory per client). Sliding counter approximates the same fix in O(1) memory by blending a weighted fraction of the previous window's count into the current one.
  • Sliding counter's approximation has its own honest quirk: right at the very first instant of a new window, its formula still counts the entire previous window's traffic as "fully present" (weight 1.0), even though a true sliding log would have already let the oldest of those requests expire. Fire "Steady (within limit)" a few times in a row and watch the counter occasionally read one stricter than the log at the exact window boundary -- verified, not a simplification.
  • All five are configured here to the same nominal budget so the comparison is fair. In production, token bucket capacity is often tuned independently of its refill rate specifically to allow bigger bursts than the sustained rate -- a knob this widget intentionally keeps locked to isolate the algorithmic difference.
