Stack, Heap & Pointers: Play With It

Three scenarios, each a classic C++ memory bug next to its fix: a pointer that outlives the stack frame it pointed into, a heap block that outlives every pointer to it, and two pointers aliasing one heap block that gets freed once too often.

Worth knowing, beyond what's animated here
  • The addresses shown (0x7ffee0010, h1, ...) are illustrative placeholders, not real ones -- real stack addresses depend on ASLR, the calling convention, and what the compiler decided to inline, and real heap addresses come from whatever the allocator's free-list looks like at that moment.
  • In the dangling-reference demo, dereferencing p after the frame pops is undefined behavior, not "guaranteed garbage." It might print 42 anyway (nothing has overwritten that stack memory yet), might print nonsense, or might crash -- and a debug build and an optimized build can genuinely disagree, which is exactly why this class of bug is so easy to ship without noticing.
  • The heap-leak demo counts a fixed 4 bytes per int block purely so the counter has something concrete to show -- the actual lesson is the shape, not the number: a block becomes unreachable the instant its last pointer goes out of scope without a matching delete, and it stays allocated for the rest of the process's life because nothing will ever call delete on it again.
  • Double-free isn't just "wasteful" the way a leak is -- it corrupts the allocator's own bookkeeping (the free-list or heap metadata), which is why glibc's malloc actively tries to detect it and abort (free(): double free detected in tcache 2) rather than silently continuing.
  • The root cause in scenarios 1 and 3 is the same idea seen from two angles: a raw pointer carries no information about who owns the memory it points to, or for how long. std::unique_ptr and std::shared_ptr exist specifically to make ownership explicit and enforce it at compile time or via reference counting instead of by convention -- that's the natural next page after this one.
