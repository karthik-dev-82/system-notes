Worth knowing, beyond what's interactive here
  • Laziness is a guarantee; the exact call count is not. Compiling this widget's own opening example in real C++20 (nums | views::filter(even) | views::transform(square) | views::take(3), GCC 13) confirms zero calls happen before iteration, and the loop never touches all 10 source elements -- but GCC's filter_view iterator eagerly searches ahead on every ++, so the real predicate call count (8, measured) runs slightly higher than the textbook minimum (6, what this widget models) needed to find 3 evens. Both are "lazy" and both short-circuit; only the standard's laziness guarantee is portable, the exact call count is an implementation detail.
  • Order changes results, not just performance. filter(even) | take(3) on 1..10 gives 2 4 6; take(3) | filter(even) gives just 2, because take already cut the input down to {1,2,3} before filter ever saw the rest. Verified against real g++ output for every stage order this widget lets you build.
  • std::ranges::to<std::vector>() is real C++23, but check your toolchain. It compiles under -std=c++23 with a recent enough libstdc++ (GCC 14+); it does not compile on GCC 13's libstdc++ even with -std=c++23 (confirmed by compiling it here). The portable eager alternative that has worked since C++20 is a constructor: std::vector<int> vec(view.begin(), view.end());.
  • The dangling-view demo above is real, confirmed undefined behavior -- compiling the "container is local" scenario with -fsanitize=address reports a genuine stack-use-after-return the moment the caller iterates the returned view, not a benign quirk. There is no compiler error at build time; nothing stops this from shipping.
  • Actions/algorithms are eager by design, not an exception to laziness. std::ranges::sort(vec) mutates vec immediately when called -- there is no pipeline to defer, because sort is not a view, it is an algorithm that runs once and produces its effect on the spot.
