Worth knowing, beyond what's animated here
  • Threading and AsyncIO can finish at the exact same total time and still behave completely differently. For CPU-bound work above, both take the same 4.05s -- but watch the glowing lane: threading jumps between all three lanes constantly (the OS preempts the GIL holder every few milliseconds, in reality), while asyncio finishes lane 1 completely, then starts lane 2. A coroutine that never hits an await holds the entire event loop hostage for its whole duration -- nothing else on that loop runs, not even an unrelated heartbeat task.
  • Multiprocessing pays real overhead that this widget shows honestly. Its head start isn't free -- spinning up a new OS process (a new Python interpreter, no shared memory) costs more than spinning up a thread or a coroutine, which is why it still wins decisively for CPU-bound work but is comparative overkill for a handful of quick I/O calls.
  • Why the summary table calls threading "fast I/O-bound" and asyncio "slow I/O-bound": with only 3 tasks the two look identical here, but that stops being true at scale. Spawning 3 threads is cheap; spawning 3,000 threads to hold open 3,000 slow connections is not -- each OS thread costs real memory (stack space) and real kernel scheduling overhead. 3,000 asyncio tasks cost barely more than 3 do, since they're just objects the single event loop juggles, not OS-scheduled entities. That's the actual reason asyncio exists, not because it's faster per task.
  • None of this changes if you switch to PyPy or add more CPU cores -- the GIL is a property of the standard CPython interpreter's memory-safety design, not a hardware limitation. It's also why multiprocessing processes don't share memory by default and need explicit IPC (pipes, queues, shared memory blocks) to talk to each other, unlike threads which share everything and need locks instead.
